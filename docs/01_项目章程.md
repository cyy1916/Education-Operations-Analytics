# 教育运营数据管理与分析项目

# 01 项目章程

## 1. 项目概述

本项目来源于在线语言教育机构的真实运营工作。

在实际工作期间，随着学生、教师、课程以及业务团队规模不断扩大，管理层逐渐发现现有的数据管理和跨部门协作方式开始出现明显问题，并要求对相关问题进行梳理和改善。

最初暴露的问题主要表现为：信息分散在大量电子表格中、不同部门之间的信息确认成本较高、排课与教师协调越来越依赖人工经验、业务状态难以持续追踪，以及部分运营指标无法快速、稳定地统计。

在进一步参与市场、销售、教务和课程运营流程后，本项目开始从单个工作问题向整体业务流程追溯，尝试识别问题真正产生的位置及其相互之间的关系。分析重点不再只是“某一张表是否需要整理”，而是进一步关注：

* 当前业务流程与数据结构是否匹配；
* 销售、运营和教务之间的信息如何传递；
* 学生、教师、课程和排课信息为何需要反复人工确认；
* 当前电子表格体系为什么随着业务规模扩大而快速增加维护成本；
* 为什么部分短期有效的业务做法会在后续产生较大的运营压力；
* 现有数据是否能够支持管理层判断业务变化产生的真实影响。

在完成业务流程梳理和数据审计后，本项目计划使用 SQL、Python 以及商业智能工具，对可以通过数据结构、数据清洗、业务规则和分析体系改善的问题进行尽可能的解决，并进一步探索未来将相关方案落地到真实内部运营流程中的可行方式。

本项目并不假设所有业务问题都可以单纯通过技术解决。技术工作的目标是减少信息分散、重复维护、人工核对和统计困难，并为跨部门协作、运营监控和管理决策提供更加可靠的数据基础。

## 2. 业务背景

### 2.1 核心业务流程

在线语言教育业务的主要学生生命周期包括：

```text
市场获客
    ↓
客户咨询
    ↓
销售跟进
    ↓
试听课程 / 水平测试
    ↓
正式报名
    ↓
课程交付
    ↓
续费 / 结课
```

不同阶段由不同团队参与，并持续产生市场、客户、学生、教师、课程、排课、反馈和续费等数据。

| 业务阶段 | 主要参与团队 | 主要数据 |
| --- | --- | --- |
| 市场获客 | 市场 / 运营 | 渠道、账号、帖子、曝光、点击与互动 |
| 客户咨询与销售跟进 | 销售 | 客户信息、咨询记录、跟进状态 |
| 试听 / 水平测试 | 销售 + 教务 | 试听安排、教师、等级评估、反馈 |
| 正式报名 | 销售 + 教务 | 学生、课程套餐、购买课时、负责人 |
| 课程交付 | 教务 | 学生、教师、课程、排课、出勤与反馈 |
| 续费 / 结课 | 销售 + 教务 | 续费、课程状态、学生状态 |

这些数据并不是独立存在的。一个学生从第一次咨询到最终结课，可能跨越多个团队、多个文件和多个业务状态，因此后续分析需要能够还原完整的学生生命周期和业务事件链条。

## 3. 项目启动时的现状

### 3.1 电子表格已经从辅助工具演变为核心运营基础设施

当前大量日常业务仍然依赖 Excel / Google Sheets 等电子表格完成：

* 数据存储；
* 信息查询；
* 客户与学生状态跟踪；
* 排课与课程安排；
* 教师协调；
* 问题记录；
* 运营统计；
* 月度汇报。

在业务规模较小时，电子表格具有灵活、成本较低、维护门槛低等优势，可以快速支持日常运营。

随着业务规模扩大，问题逐渐从“某张表不好维护”演变为“业务对象被拆散在大量独立文件中”。同一个客户、学生、教师或课程可能在多个文件中重复出现，不同团队也可能维护各自版本的信息。

### 3.2 当前原始数据规模

根据项目启动阶段能够确认的实际工作规模，现有原始业务数据已经具有明显的分散特征。

#### 班课数据

近两年内，线上和线下 A1、A2、B1、B2 班课均按照等级和授课形式分别建立独立表格。

目前估算：

* 线上班课每个等级约有 80–100 份独立表格；
* 线下班课每个等级约有 20–40 份独立表格；
* 如果按照 A1、A2、B1、B2 四个等级计算，仅班课相关表格就约有 400–560 份。

上述估算尚未包含所有独立课程安排表、汇总表以及其他辅助运营表格。

#### 私教数据

近四年私教课程中：

* 当前仍在管理或有记录的私教课程超过 150 组；
* 已停课的私教课程约 30–40 组；
* 仅按照当前能够确认的课程组计算，私教历史记录规模已经超过约 180 组。

#### 课程安排数据

课程安排表并未集中在一个统一的数据源中，而是继续按照：

```text
课程等级
    +
线上 / 线下
    ↓
不同课程安排表
```

分别维护。

因此，当前需要处理的并不是单一数据集，而是跨多年、跨等级、跨线上线下授课形式、跨班课和私教课程的大量分散业务文件。

详细的数据来源、文件类型、字段结构、维护人员和历史范围将在后续《03 当前状态分析》以及数据清单中进一步展开。

### 3.3 当前跨部门协作问题

除了数据分散之外，项目启动过程中还发现一个对业务影响较大的跨部门问题：销售、运营和教务之间的目标、责任与信息确认机制存在脱节。

在部分客户沟通中，出现了教师可用时间和课程安排尚未经过教务确认，就已经向客户做出承诺，甚至与教师实际可用时间不一致的情况。

这种做法可能在短期内降低销售沟通阻力并提高客户转化，但后续需要由教务重新寻找教师、调整课程时间、协调学生和教师，从而将前端销售阶段没有处理的约束转移到课程交付阶段。

实际工作中观察到的后续现象包括：

* 教务排课与教师协调工作量明显增加；
* 重复确认和临时修改增加；
* 排课及信息传递失误风险增加；
* 短期客户转化率曾出现提升；
* 约两个月后，客户转化表现出现明显下降；
* 同期教师离职率明显上升。

目前这些现象可以说明不同业务阶段之间存在值得重点分析的时间关联和运营机制，但在完成后续数据分析之前，本项目不会直接将转化率下降或教师离职率上升全部归因于单一决策。

该问题将在《03 当前状态分析》中作为重点运营案例进一步拆解，并在后续数据分析和数据看板中尝试量化其影响。

## 4. 核心问题定义

结合现有工作流程和初步数据审计，本项目将当前问题归纳为以下几个核心方向。

### 4.1 数据分散与重复维护

同一个业务对象可能同时存在于咨询、试听、报名、学生管理、课程安排和课程记录等多个文件中，需要通过人工方式进行关联和核对。

### 4.2 业务流程与数据结构不匹配

当前表格主要按照实际工作需要逐步增加，但并未始终按照客户、学生、教师、课程、报名、排课、课程执行等稳定业务实体设计，因此容易出现一个表同时承担数据存储、工作任务和状态跟踪等多种职责。

### 4.3 缺少统一的数据定义和唯一标识

相同课程、学生状态或业务对象可能存在多种记录方式，不同文件之间也缺少稳定的唯一编号进行关联。

### 4.4 历史状态难以追踪

部分业务状态通过直接修改原有单元格进行维护，因此可以看到“当前结果”，但难以准确还原“过去发生过什么”。

### 4.5 大量工作依赖人工协调和个人经验

排课、教师协调、学生通知、异常处理、状态更新和月度统计仍高度依赖员工手工操作和经验判断。

### 4.6 跨部门目标和信息确认机制不一致

销售转化目标与教务实际交付约束之间缺少稳定的数据确认机制，容易出现前端承诺与后端资源不匹配的问题，并将成本和风险向后续课程交付环节转移。

### 4.7 缺乏稳定的业务分析和决策支持能力

现有数据体系主要用于完成日常工作，而不是为跨部门分析和管理决策设计，因此管理层难以快速判断市场渠道、销售转化、课程执行、教师负荷、学生留存以及关键运营变化之间的关系。

上述问题的详细证据、具体流程、案例和数据结构不在本文件中展开，而将在《03 当前状态分析》中集中说明。

## 5. 项目目标

### 5.1 还原真实业务流程和问题产生机制

梳理市场、销售、教务以及课程交付之间的信息流和工作流，明确问题发生的位置、参与角色以及向下游传递的方式。

### 5.2 建立统一的数据基础

对当前分散的数据来源进行审计，建立数据清单和数据字典，并逐步统一核心业务对象、字段定义和标识方式。

### 5.3 建立可追踪的数据模型

根据真实业务流程重新识别客户、学生、教师、课程、报名、排课、课程执行、续费等核心实体和业务事件，使当前状态和历史变化都能够被分析。

### 5.4 使用 SQL 和 Python 降低重复人工处理

通过 SQL 建立结构化的数据查询和业务关系，通过 Python 完成数据清洗、批量整合、字段标准化、历史文件处理和可重复的数据转换流程，尽可能减少人工复制、核对和重复统计。

### 5.5 建立面向运营和管理层的分析能力

通过统一指标和商业智能数据看板，使市场、销售、运营和教务能够基于同一数据基础观察业务表现，并支持转化、课程执行、教师负荷、学生留存和运营风险分析。

### 5.6 为后续真实落地提供实施方案

在完成分析和原型验证后，进一步评估如何在不一次性替换现有工作方式的情况下，将统一的数据结构、录入规则、查询方式和数据看板逐步交给内部工作人员使用。

## 6. 项目可行性分析

本项目不仅需要判断技术上“能不能做”，还需要判断投入是否合理、内部人员是否能够使用，以及现有业务流程是否具备落地条件。因此，项目可行性从经济、技术和运营三个方向进行评估。

### 6.1 经济可行性

#### 6.1.1 预估成本构成

本项目现阶段的主要成本并不是采购大型企业系统，而是整理现有业务、清洗历史数据和建立新的数据基础所需要的内部工作时间。

主要成本包括：

| 成本类别 | 主要内容 | 当前预估 |
| --- | --- | --- |
| 数据审计与整理成本 | 识别数百份班课表格、私教记录、排课表和其他历史文件 | 较高的一次性人工成本 |
| 数据清洗与迁移成本 | 统一字段、课程名称、人员信息、状态和历史记录 | 中高的一次性成本 |
| 技术开发成本 | SQL 数据结构、Python 清洗与转换脚本、分析查询 | 以内部开发工时为主 |
| 软件与基础设施成本 | 数据库、文件存储、BI 工具和可能的云服务 | 可从较低成本方案开始，具体取决于现有授权和部署方式 |
| 培训与流程调整成本 | 员工学习新的录入规则、确认流程和数据看板 | 中等的导入成本 |
| 后续维护成本 | 新字段、业务规则、人员权限和数据质量维护 | 持续但可控 |

如果优先使用 Python、SQL 数据库以及现有办公和 BI 环境，早期软件采购成本可以保持相对较低。真正需要重点评估的是历史数据整理和业务流程重新标准化所需要的人工时间。

#### 6.1.2 预期经济收益

项目完成后潜在经济收益主要来自以下几个方向：

* 减少教务在多个文件之间查找和核对信息的工作时间；
* 减少因错误排课、错误承诺和重复沟通产生的返工成本；
* 降低月度统计和业务汇报的人工整理成本；
* 降低由于信息不同步导致的课程调整和客户服务成本；
* 提高真实可交付前提下的有效客户转化质量，而不仅关注短期转化数量；
* 通过更早识别教师负荷和运营异常，减少教师流失和重新招聘、重新协调课程产生的成本；
* 通过学生留存和续费分析，减少可以被提前发现的学生流失。

当前尚缺少完整的员工人工成本、平均课程收入、学生生命周期价值、教师招聘替换成本和错误事件成本，因此本阶段不人为填写缺乏依据的具体金额。

后续可以使用以下框架建立项目投资回报估算：

```text
项目总成本
=
数据整理与开发工时成本
+ 软件 / 基础设施成本
+ 培训与迁移成本
+ 持续维护成本
```

```text
年度可量化收益
=
节省的人工工时价值
+ 减少的错误与返工成本
+ 减少的学生流失对应贡献
+ 减少的教师流失与替换成本
+ 更稳定的有效转化带来的新增贡献
```

当后续分析能够获得足够的业务数据后，再对上述成本和收益进行货币化估算，避免为了展示 ROI 而制造没有依据的数字。

### 6.2 技术可行性

从现有问题看，大部分数据管理和分析问题可以使用成熟的数据技术进行改善，不需要从一开始开发复杂的企业级系统。

#### 6.2.1 可使用的主要技术

| 技术方向 | 主要用途 |
| --- | --- |
| SQL / 关系型数据库 | 建立统一的客户、学生、教师、课程、报名、排课和课程执行关系 |
| Python | 批量读取历史文件、清洗数据、标准化字段、合并数据、生成可重复的 ETL 流程 |
| 数据字典与业务规则 | 统一字段含义、课程分类、状态定义和可接受取值 |
| 唯一标识与关系模型 | 减少通过姓名、微信或人工判断匹配不同文件的问题 |
| 商业智能工具 | 建立统一 KPI、转化漏斗、课程运营、教师负荷和学生留存数据看板 |
| 数据校验规则 | 在录入或导入阶段识别缺失、重复、时间冲突和非法状态 |

#### 6.2.2 主要技术难点

项目最大的技术难点并不是 SQL 语法或 Python 编程本身，而是历史数据是否足够一致并能够被可靠关联。

主要风险包括：

* 历史表格数量大，结构可能随时间变化；
* 同一字段在不同文件中可能使用不同名称；
* 同一学生或教师可能缺少统一编号；
* 部分历史状态已经被覆盖，无法完整恢复；
* 线上、线下、班课和私教存在不同业务规则；
* 业务规则可能主要存在于员工经验中，而不是正式文档；
* 如果原始数据输入继续不受控制，数据库和看板仍可能继承错误数据。

#### 6.2.3 技术实施前提

为了使技术方案有效，需要至少满足以下前提：

* 建立可追溯的原始文件清单，并保留历史原始版本；
* 确认核心业务实体及其唯一标识策略；
* 建立统一的数据字典和状态定义；
* 明确班课、私教、线上和线下课程的不同业务规则；
* 建立销售承诺、教师可用时间和教务确认之间的数据关系；
* 对不能恢复的历史信息进行明确标记，而不是强行补全；
* 对敏感学生、家长和教师信息建立访问和匿名化规则。

因此，从技术角度看，本项目具有较高可行性，但技术效果高度依赖业务规则标准化和原始数据质量。

### 6.3 运营与操作可行性

技术方案只有真正进入员工日常工作流程，才能减少现有问题。如果最终仍然要求员工同时维护旧表格和新系统，反而可能增加工作量。

因此，未来正式落地应优先采用渐进式方式，而不是一次性替换全部电子表格。

#### 6.3.1 建议的落地路径

```text
第一阶段：数据标准化
统一核心字段、状态、课程命名和唯一编号
    ↓
第二阶段：历史数据整合
使用 Python 批量清洗和导入现有表格
    ↓
第三阶段：统一数据存储
使用 SQL 数据库维护核心业务实体和历史记录
    ↓
第四阶段：保留简单录入入口
通过员工熟悉的表格 / 表单 / 简单业务界面进行数据录入
    ↓
第五阶段：自动校验与跨部门确认
对教师时间、课程安排、状态变化等关键数据增加校验和确认规则
    ↓
第六阶段：统一数据看板
向销售、运营、教务和管理层提供不同权限和视角的指标
    ↓
第七阶段：逐步减少重复表格
在稳定运行后取消不再需要的重复维护文件
```

#### 6.3.2 对内部工作人员的影响

正式落地时需要重点控制以下问题：

* 不要求非技术员工直接操作 SQL 或 Python；
* 尽量保留简单、熟悉的数据录入方式；
* 明确销售、运营和教务分别负责哪些字段；
* 对教师时间和课程安排设置明确的确认责任；
* 避免同一数据同时由多个团队重复维护；
* 为常见异常建立标准处理流程；
* 对核心数据变更保留历史记录；
* 根据岗位提供不同的数据访问权限；
* 在正式推广前先选择有限业务范围进行试运行。

运营落地的关键并不是让员工学习更多技术，而是让新的数据结构减少他们需要记忆、查找、重复确认和手工统计的内容。

## 10. 数据隐私与公开原则

实际业务数据包含敏感信息，例如：

* 学生个人信息；
* 家长联系方式；
* 教师个人和工作信息；
* 客户沟通记录；
* 内部运营记录；
* 员工工作和业务表现数据。

因此，公开版本不会直接发布真实业务数据。

公开仓库中的数据将采用以下方式处理：

* 使用模拟数据；
* 删除敏感字段；
* 对个人信息进行匿名化；
* 对内部员工、教师和客户信息进行脱敏；
* 根据真实业务逻辑构造可以复现分析方法的示例数据。

业务流程、数据结构和分析逻辑可以来源于真实工作经验，但公开数据必须与真实个人和内部敏感信息隔离。

## 11. 项目定位

本项目是一项从真实运营问题出发的数据管理与分析改进工作。

项目的核心逻辑是：

```text
管理层发现运营问题
    ↓
进入真实工作流程定位问题
    ↓
分析问题产生机制和跨部门影响
    ↓
审计现有原始数据
    ↓
重新设计数据结构和业务规则
    ↓
使用 Python 与 SQL 进行数据整理和分析
    ↓
使用数据看板验证业务变化和运营影响
    ↓
提出可以逐步落地到真实内部工作的改进方案
```

项目的重点不是为了展示某一种工具，也不是单独开发一个新的业务系统，而是尝试回答一个更实际的问题：

> 当在线教育业务随着学生、教师、课程和内部协作规模增长后，原本依赖大量电子表格和人工经验的运营方式开始失去可扩展性时，如何从真实业务流程出发，重新建立能够被追踪、分析并逐步落地使用的数据基础？

SQL、Python、数据模型和商业智能工具只是解决问题的手段。最终目标是降低重复人工工作和信息失真，使销售、运营、教务和管理层能够基于更加一致的数据进行日常协作和业务决策。
